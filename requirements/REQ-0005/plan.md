# 实施计划

## 方案

先为现有 Harness 建立可测试的证据模型，再逐项替换当前基于自由文本、工作树状态或文件存在性的弱校验。所有新增检查通过统一 Harness 命令暴露，使本地 Agent 与 CI 使用完全相同的路径。

## 步骤

- [ ] 定义 Approval Snapshot、授权审批者、基线、审计结果、PR 接受证据和 Exception Record 的机器可读结构。
- [ ] 为当前弱校验编写失败测试，覆盖 actor 伪造、干净工作树 diff、缺失 PR 证据和无效例外。
- [ ] 将范围证据改为基线提交到 HEAD 的 Git diff，并校验需求目录与允许范围。
- [ ] 实现敏感信息与依赖审计适配器，保存脱敏摘要并让失败进入统一门禁结果。
- [ ] 强化状态转换，使批准、验证和完成状态只能由对应证据驱动。
- [ ] 让 PR Package 汇总真实 diff、全部审计结果、例外和已知基线缺口。
- [ ] 增强 `harness:doctor`，检查运行所需工具与配置但不读取真实凭据。
- [ ] 更新流程文档、词汇表和 ADR，并提供对已有需求状态的兼容或迁移说明。
- [ ] 在干净隔离状态运行完整 Harness 验证并进行独立审阅。

## 验证计划

- AC-001：构造已提交变更且工作树干净的测试仓库，验证 PR Package 仍列出 base...HEAD 路径。
- AC-002：分别测试有效审批快照、任意 actor 字符串和内容哈希失配。
- AC-003：为六类强制门禁分别注入失败，确认均阻止 `review-ready`。
- AC-004：测试缺字段、未授权、过期与有效例外。
- AC-005：测试缺失、关闭未合并、明确接受与已合并 PR 证据。
- AC-006：在隔离 runtime 中制造基线失败并验证当前需求被阻塞。
- AC-007：运行 Harness 自动化测试套件。
- AC-008：运行 doctor、文档审阅及全局 `check`、`test`、`build`。

## 回退

以单独提交引入证据结构和各门禁适配器。若新门禁造成错误阻塞，可回退对应实现提交并保持文档声明不被提前启用；不得以关闭检查作为永久回退。
