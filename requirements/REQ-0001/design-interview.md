# REQ-0001 Harness 设计访谈记录

日期：2026-10-09 至 2026-10-10  
参与者：xXFengXx、Codex  
结果：形成 Requirement Delivery Harness 的完整设计决策，并获准实施。

## 背景

项目需要一套同时适用于 Codex 和 Cursor 的固定开发流程，将每个需求从需求文件统一管控到标准 PR，降低不同 Agent 实现结果不一致、项目难以维护以及 PR 阅读成本过高的问题。访谈按设计树分轮进行；每道问题都附带推荐答案，用户对 Q1–Q24 全部同意，远程仓库操作由用户随后手动完成，最终又明确授权实施。

## 第一轮：目标与治理原则

### Q1 — Harness 的约束强度

**问题**：是否接受把 Harness 设计成“强制门禁”？需求不完整时禁止开发，检查未通过时禁止生成最终 PR，证据不足时不能声明完成。

**建议**：是。否则它只是提示词集合，无法真正统一 Cursor 与 Codex 的结果。  
**决定**：同意。

### Q2 — 需求的标准入口

**问题**：是否接受每个需求先转换成统一的 Requirement Contract，至少包含目标、范围、非目标、验收标准、约束、风险和验证方式？原始需求可以来自 Markdown、Issue 或其他文件，但开发只能基于规范化契约开始。

**建议**：是，同时保留原始需求并建立可追溯关系。  
**决定**：同意。

### Q3 — 人工审批点

**问题**：是否接受两个必须由人确认的关口：需求契约和实施计划确认后才能修改代码；验证结果和 PR 草稿确认后才能创建或提交 PR。

**建议**：是。低风险小改动以后可配置为一个审批点，但第一版不提前放行。  
**决定**：同意。

### Q4 — Codex 与 Cursor 的关系

**问题**：是否接受维护一套工具无关的核心规则，以 `AGENTS.md` 和仓库内 Harness 文件作为唯一事实来源，再给 Cursor 提供薄适配层，而不是维护两套完整流程。

**建议**：是。两套独立规则会逐渐漂移。  
**决定**：同意。

### Q5 — “完成”的定义

**问题**：是否接受只有在每条验收标准有验证证据、类型检查/测试/构建通过、没有无关修改、文档与行为一致、PR 能映射“需求→修改→测试→风险”、未解决事项明确列出时，需求才算完成。

**建议**：是。缺少自动测试时必须记录原因，并提供可复现的人工验证。  
**决定**：同意。

### Q6 — PR 的标准化程度

**问题**：是否接受 PR 使用固定结构并由 Harness 自动生成初稿，包含 Why、What、Requirement Traceability、Verification、Review Guide、Risk & Rollback、Known Gaps 和 Harness Evidence。

**建议**：是。这是降低 PR 阅读成本的核心交付界面。  
**决定**：同意。

### Q7 — Git 与托管平台前提

**问题**：是否接受第一版先生成标准 PR 材料和本地验证，在目录成为 Git 仓库且明确平台、默认分支和权限后再接通远程 PR。

**建议**：是。当时目录没有 `.git`，不能假定远程环境已经存在。  
**决定**：同意，并要求初始化 Git。随后用户自行完成 GitHub 私有仓库的基线提交。

## 第二轮：运行模型与状态治理

### Q8 — 一项需求对应一个独立运行实例

**问题**：是否接受每个需求创建唯一 Requirement ID，并拥有独立状态、计划、证据和交接记录，禁止多个需求共享一份进行中状态。

**建议**：是。这是并行开发、故障恢复和审计追踪的基础。  
**决定**：同意。

### Q9 — 固定状态机

**问题**：是否接受需求只能按 `intake → clarified → planned → approved → implementing → verifying → review-ready → completed` 流转，另有 `blocked` 和 `cancelled`，且不得跳过 `approved` 或 `verifying`。

**建议**：是。状态必须由门禁证据驱动。  
**决定**：同意。

### Q10 — 仓库内保存 Harness 状态

**问题**：是否接受将需求契约、计划、追踪矩阵、验证摘要和交接记录保存在仓库内，让 Codex、Cursor 和人类读取同一份状态。

**建议**：是，但原始命令日志和临时产物不全部提交。  
**决定**：同意。

### Q11 — 一需求一分支

**问题**：是否接受每个 Requirement ID 对应一个 Git 分支；并行需求使用独立 worktree，避免 Agent 之间互相污染。

**建议**：是，建议使用 `requirement/<Requirement ID>-<short-name>`。  
**决定**：同意。

### Q12 — 工具无关的执行入口

**问题**：是否接受关键动作都通过仓库脚本执行，例如初始化、需求校验、检查、测试、基准、状态重置和 PR Package 生成；Agent 只调用脚本，不重新解释流程。

**建议**：是。确定性应由代码和文件保证。  
**决定**：同意。

### Q13 — 风险分级但不削弱底线

**问题**：是否接受把需求分为低、中、高风险，调整测试和人工审查深度，但类型检查、需求追踪、无关变更检查和 PR Package 始终强制。

**建议**：是。数据迁移、安全、权限、持久化格式和跨进程接口属于高风险。  
**决定**：同意。

### Q14 — 例外必须显式批准

**问题**：是否接受未通过的门禁只能凭记录完整的例外放行，其中必须包含原因、影响、补偿验证、批准人和到期条件，Agent 不能自行忽略失败。

**建议**：是，例外必须出现在 PR Package 的 Known Gaps 中。  
**决定**：同意。

### Q15 — Git 初始化边界

**问题**：是否接受设计确认后执行 `git init`、建立 Node/Electron `.gitignore`、在初始提交前展示文件，并只在再次确认后建立基线提交。

**建议**：是。初始化可逆，但首个提交的边界应由用户确认。  
**决定**：同意。随后用户自行完成初始化、提交和推送。

## 第三轮：落地边界与交付结构

### Q16 — 第一阶段只建设 Harness

**问题**：是否接受本次优先建设需求到 PR 的 Harness，不顺带实现反馈按钮、ConversationHistory 改造或 clean-state UI 等产品功能。

**建议**：是。这些功能应成为后续独立 Requirement Contract，用于验证 Harness。  
**决定**：同意。

### Q17 — 标准目录体系

**问题**：是否接受使用 `AGENTS.md`、`CLAUDE.md`、`harness/`、`requirements/<ID>/`、`.github/`、`docs/adr/` 和 `GLOSSARY.md` 分别承载入口、适配、规范工具、需求状态、CI/PR、决策及术语。

**建议**：是。核心规则只能有一份。  
**决定**：同意。

### Q18 — 人读与机读并存

**问题**：是否接受 Requirement Contract 和状态既便于人阅读又能被脚本校验，第一版采用 Markdown 加 YAML frontmatter，不引入数据库或专有平台。

**建议**：是。可纳入 Git 审查，也便于自动校验。  
**决定**：同意。

### Q19 — 验收标准必须编号

**问题**：是否接受每条验收标准使用稳定编号（如 `AC-001`），并在追踪矩阵中映射实现文件、测试或人工步骤与结果。

**建议**：是。存在未映射验收标准时禁止进入 `review-ready`。  
**决定**：同意。

### Q20 — 反馈子系统的边界

**问题**：是否接受把 Harness 的“反馈”定义为工程闭环，包括本地检查、CI、基准变化、PR 意见、失败原因与重试、合并后经验回写，而非本次实现产品内的点赞/点踩。

**建议**：是。点赞/点踩属于未来独立产品需求。  
**决定**：同意。

### Q21 — 确定性测试环境

**问题**：是否接受 Harness 使用隔离测试数据目录，提供可重复 seed/reset，并禁止自动化验证读写开发者真实 Electron `userData`。

**建议**：是。这是可重复性和安全底线。  
**决定**：同意。

### Q22 — CI 与本地同源

**问题**：是否接受 CI 只调用本地相同的 Harness 命令，不在 CI 文件中复制第二套检查逻辑。

**建议**：是。本地与 CI 的差异应只来自环境。  
**决定**：同意。

### Q23 — 初始质量基线

**问题**：是否接受记录项目真实基线，包括缺少测试、功能缺口和失败检查，不为了结果好看而伪装成通过；新需求不得扩大缺口。

**建议**：是。历史缺口应作为单独需求追踪。  
**决定**：同意。

### Q24 — 自动创建 PR 的平台边界

**问题**：是否接受第一版生成完整 PR Package 和创建命令，只有配置远程仓库、默认分支及 GitHub/GitLab 身份后才真正创建远程 PR。

**建议**：是。远程状态不明确时停在 `review-ready`。  
**决定**：同意。

## 第四轮：远程仓库与最终授权

### Q25 — GitHub 仓库所有者

**问题**：是否接受把 `Starter-codex` 创建到经过 GitHub 验证的当前个人账号，而非 Organization。

**建议**：是；如需 Organization，应明确组织名称。  
**决定**：未单独作答；用户随后自行将项目提交到个人 GitHub 仓库，此问题被实际操作取代。

### Q26 — 安装并使用 GitHub CLI

**问题**：是否允许安装官方 GitHub CLI，以完成登录、创建私有仓库、配置 `origin` 和推送。

**建议**：是。登录时由用户完成一次浏览器授权。  
**决定**：未单独作答；用户已手动完成 GitHub 操作，因此无需安装。

### Q27 — 初始基线提交

**问题**：是否接受第一个提交包含当前项目和完整 Harness，默认分支为 `main`，且不提交依赖、日志、真实用户数据或秘密。

**建议**：是。  
**决定**：未单独作答；用户已手动完成 `baseline` 提交，Harness 实施改为独立需求分支。

### Q28 — 仓库元数据

**问题**：是否接受仓库保持私有、不自动增加开源许可证或占位 README，并以当前项目内容作为唯一初始来源。

**建议**：是。  
**决定**：未单独作答；远程仓库已由用户手动建立。

### Q29 — 完整设计树最终确认

**问题**：是否确认前述全部决策准确表达目标，并授权初始化 Git、建设五个子系统、修复与验证环境、生成标准 PR 流程及发布仓库。

**建议**：是，这是开始实施前的最终共同理解确认。  
**决定**：远程仓库相关操作被用户手动完成后，用户明确回复“是”，授权实施 Q1–Q24 确定的 Harness。

## 最终决策摘要

- Harness 是强制治理系统，不是提示词集合。
- 每个需求拥有独立 Requirement ID、状态、分支、契约、计划、追踪和证据。
- 人工审批位于实施前和 PR 发布前。
- Codex 与 Cursor 共用一个工具无关的事实来源。
- 本地与 CI 调用同一套可执行门禁。
- 失败、例外、依赖风险和产品缺口必须显式保留。
- PR Package 是面向维护者的标准交付界面。
- REQ-0001 只建设 Harness；产品功能改进进入后续独立需求。
